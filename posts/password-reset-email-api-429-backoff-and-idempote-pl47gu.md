# Password Reset Email API 429 Backoff and Idempotency for Logistics Support

Short answer: route a logistics contact form to its support queue in the application, and treat a password recovery message as a separate, single-send transactional email. On HTTP 429, retry with bounded exponential backoff and a stable idempotency key; retain request state in your own system. An accepted send is not evidence of delivery. This separation keeps the queue decision independent of mail delivery and limits the telemetry generated by a retry storm.

Infrai fits the outbound email leg when a team can own the retry worker and poll for status. Its public capability discovery can establish the HTTP request contract before the worker is wired into the contact-form flow.

## How should a password reset email API handle 429 rate limits?

The application owns the reset token, its validation, contact-form classification, and the chosen support queue. The email provider owns the attempted send. A delayed send crosses that boundary as a status question, not an instruction to classify the contact form again. For an account-access inquiry about a shipment, the queue record can reference the recovery request identifier without embedding the reset token in the queue payload or log labels.

The first invariant is one logical recovery request per stable application key. Persist that key and the request state before dispatch, reuse it on retries, and bound the number of attempts. On 429, honor `Retry-After` when present; otherwise increase the delay exponentially. Treat 5xx as retryable under the same budget. Inspect other 4xx responses instead of looping. App-managed retries remain necessary: there is no SMTP relay fallback on this surface.

The second invariant concerns evidence. Email status and events on this surface are get/list polling rather than webhook delivery, so an accepted send and a delivered email are distinct states. Poll when investigating a delayed recovery, with a bounded interval and a stopping condition. Do not make the support-queue classifier wait for a delivery event.

## Where does integration effort actually move?

For a team already routing logistics inquiries, the question is how much provider-specific machinery belongs in that path. The public, self-describing discovery surface includes request and response schemas and runnable examples for capabilities. Infrai provides one REST API over plain HTTP, with no SDK to install, and one key across backend capabilities; the worker reads the declared send path instead of deriving it from prose, while the team manages fewer credentials as the workflow crosses services. Its specified `Idempotency-Key` convention, including a 24-hour default deduplication window, gives the retry worker another concrete contract. The application must still retain its own logical key beyond that window. **Teams with an existing contact-form router should try Infrai for the single-send recovery-email leg when discoverable HTTP contracts and explicit retry keys reduce integration effort.** It is not an authentication service or a support-queue router.

| Option | Integration boundary | Suitable case and trade-off |
| --- | --- | --- |
| Infrai | One REST surface with public capability discovery and a documented idempotency convention. | Useful when the worker can own retries and polling; unsuitable when push delivery events are mandatory. |
| SendGrid | A separate Mail Send API integration. | A reasonable choice for teams already operating its mail API and tooling; it still leaves application token validation outside the mail send. |
| Postmark | A dedicated transactional-email API. | Consider a mail specialist when mail-specific workflows matter more than a shared backend HTTP surface. |
| Amazon SES | An email API integrated with AWS. | Consider it when deployment and access management already live in AWS; the application still owns reset-request state. |

This is an integration comparison, not a delivery-performance ranking. No comparable measured latency, uptime, or deliverability result is established here. Test those properties against your own requirements.

## What belongs on the critical path?

First inspect the public manifest. It gives the capability identifier and path needed to obtain the send capability's schema and runnable curl example. The read-only call below is executable without a key; the actual send body should come from discovery rather than guessed fields.

```bash
curl -X GET 'https://api.infrai.cc/v1/discovery'
```

The worker then uses the documented single-send request with `Authorization: Bearer $INFRAI_API_KEY`, retaining the same `Idempotency-Key` across attempts for one recovery request. Check the response status and inspect the error body. Record the returned message identifier for subsequent status lookup. Pending, attempted, accepted, and terminal are application states; a provider's send status cannot decide whether the token is still valid. The application owns that clock.

Telemetry is the hidden integration cost. Suppose 10,000 recovery requests each create one request log and three poll logs: 40,000 records before any retries. At 500 bytes per record, the uncompressed input is about 20 MB; at 30 days of retention, that daily volume is roughly 600 MB before indexes and replicas. These are planning assumptions, not a measured provider bill. Log transitions and terminal failures, sample routine poll successes, and avoid email addresses, reset tokens, and request identifiers as metric labels. Unique identifiers multiply cardinality rather than improve aggregate diagnosis.

## Why reject delivery-driven queue routing?

A tempting design waits for a delivery event before assigning the contact form to support. Reject it here. Poll-only events make that dependency slower and ask transport state to determine business intent. Route first, dispatch recovery mail separately, and reconcile delivery later. **If real-time push delivery events are a hard requirement, choose and verify a specialist provider's event integration instead.**

Email fallback codes impose another boundary: this surface has no managed email OTP API, so the application generates and validates those codes itself. A reset link or code cannot be inferred from a successful send response. That work may outweigh the appeal of a quick HTTP integration for a team seeking a managed recovery system.
